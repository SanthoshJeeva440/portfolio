Automation Pipelines

A Jenkins pipeline-as-code project that runs a scheduled health check against my GitHub profile page and README, archives JSON and Markdown reports, and emails a failure summary. Pipeline logic and configuration live in separate repositories.

Repository (opens in a new tab)
Jenkins declarative pipeline Python 3 requestsBeautifulSoupPyYAMLEmail Extension Docker (Jenkins setup)

Problem

Profile READMEs depend on third-party stats cards and images that can break silently, sometimes returning HTTP 200 with an error image. A manual check doesn't scale and is easy to forget.

How it works

  • automation-pipelines holds the Jenkinsfile; automation-ci-config holds the YAML config, requirements, and the Python checker.
  • The pipeline checks out the config repo, reads jenkins.cron from YAML, and sets its own schedule trigger.
  • A virtualenv installs pinned dependencies and runs check_profile.py, which checks the live profile page, required text, the raw README, and every README image, including SVG error markers such as "API rate limit exceeded".
  • Reports are always archived. On failure, an email with the Markdown report and JSON attached goes out, with a fallback recipient if config checkout itself failed.
  • jenkins-setup defines a Docker image for Jenkins (setup wizard skipped, admin bootstrapped by Groovy) with a Render deployment spec.

My contribution

Designed and wrote the pipeline, the config schema, the checker, and the Jenkins container setup.

Web Automation Frameworks

Two framework styles for the same kind of problem: a Java + Selenium + TestNG framework built on page objects, and a Python Robot Framework suite with BDD keywords, parallel execution, and CI on both Jenkins and GitHub Actions.

Robot Framework repo (opens in a new tab) Java repo (opens in a new tab)
Selenium 4 Java TestNG Maven Robot Framework Python PabotExtent Reports Jenkins GitHub Actions

Problem

UI suites become brittle and slow when locators, data, and environments are hard-coded. These frameworks keep each concern in its own layer so tests stay readable and run against any environment.

Architecture

  • Java: page object classes with a PageObjectManager, a shared SeleniumMethods base, and per-environment properties (dev, qa, stage, prod) chosen with -Denvironment.
  • TestNG suite XML runs the same e2e package on Chrome, Firefox, and Safari; WebDriverManager handles drivers; Extent Reports for HTML output.
  • Robot Framework: page-object resources, keyword resources, and a core browser layer, with YAML test data per environment selected by -v env:.
  • Gherkin-style BDD tests, tags for smoke, regression, and e2e, and Pabot to run the smoke suite in parallel per user credential.
  • CI: a Jenkinsfile publishes GitHub Checks per stage; a GitHub Actions workflow runs the suite headless and uploads the report as an artifact.

My contribution

Built both frameworks end to end, including the CI configuration.

Mobile Automation Framework

A Robot Framework + Appium project that automates the same user journey on Android and iOS from one codebase, with switchable local and remote device configuration and packaging scripts for running on a remote device cloud.

Repository (opens in a new tab)
Appium AppiumLibrary Python Android iOS Shell packaging

Problem

Android and iOS versions of an app usually share user journeys but differ in locators and launch details. Keeping two separate suites doubles maintenance.

Architecture

  • Shared test intent with platform-specific page objects and keywords for Android and iOS.
  • A device configuration module switches between a local real device and remote CI devices with one variable (Tester = 'Remote').
  • Android launch by app package and activity, with auto-granted permissions and screenshots captured on failure.
  • run_android.py and run_ios.py wrap Robot's CLI with project paths; create-test-zip-*.sh and run-tests-*.sh package and run the suite on a remote device host.

My contribution

Built the framework structure, device configuration, and run and packaging scripts.

UiAutomator2 and Maestro are part of my professional mobile work; this public sample uses Appium with AppiumLibrary.
